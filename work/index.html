The work above the waterline.

OpenCorral is an open-source station that sits above the coding and media harnesses people already use. The part no tool ships yet is a local record, built from your own work, of which harness and model pairing succeeds at which kind of task. This page sets out the five pieces of work that build that record, so you can pick one to own.

See the five lanes How to join

Where the line falls.

The project's charter draws a waterline. Below it, functionality is commodity, shipped by harness vendors and by many open projects, and OpenCorral builds none of it. Above it is the work that only a layer seeing every harness's results can do.

Waterline: below this line is commodity

Runs and governs many agents

Execution orchestrators and meta-harnesses: parallel agents, worktrees, pull requests, spend policies. OpenCorral is designed to plug in above them.

Harness: one model, one tool loop

Claude Code, Codex, Cursor, OpenCode, Gemini CLI and others. OpenCorral works with them by relay today and never replaces them.

The acceptance gate sits above the line, and it is now shared ground. Research agrees it matters: Proof-or-Stop (July 2026) reports that its evidence-gated loop cut the injected cases that passed visible tests and failed hidden ones from 31 of 1,800 under a compute-budgeted naive loop to 2 of 1,800. OpenCorral has the gate because the record needs it. The record is the reason the project exists.

Why a record.

Pairings can differ on the same work in ways their own tests do not show. In the project's first paired run, six builds of one task all passed their own tests and the project's full verification, and hidden checks still found a defect in three of them.

Outside the project, Peter van Onselen graded six harness and model pairings, five runs each, against a hidden test suite. Swapping the model inside one harness moved its score from 85 to 97 of 100.

Public benchmarks score pairings on shared tasks. A person choosing who gets the next job needs the same measurement on their own kinds of work, kept on their own machine.

Words used here.

Pairing
One harness, one model and one configuration on one machine. The charter also calls it an employee.
Objective
What you want made, with the outputs it requires and the criteria that decide acceptance.
Capability surface
The record the project is building: outcomes counted by pairing, by kind of task and by machine, each count shown with its denominator and its unknowns. The charter calls a pairing's demonstrated range its sapescape.
Private checks
Tests or probes written by someone other than the builder and kept from the builder, so the builder cannot aim at them.
Steward
The person who owns the objective and makes the judgments a machine cannot.

What runs today.

The repository holds a working local preview of slice S1: about 1,300 lines of TypeScript with no runtime dependencies, a SQLite journal on Node 24, and a station served only on your own machine. Its 13 tests pass, payload validators in Node and Python agree on 56 cases, and continuous integration runs on Ubuntu and Windows.

It records each objective, each work order relayed to a service, each returned file as exact bytes with a SHA-256 hash, each check and judgment, and each acceptance decision, and it exports all of it as JSON. Those records are the raw rows the capability surface will be built from.

The five lanes.

Each lane belongs to a slice of the implementation plan, which states the evidence that ends it. A lane is a part you can own.

1

The capability record

Slice S5
Above the line
Public benchmarks score pairings on shared tasks. The record on a person's own work can only be built by a layer that sees every harness's results.
What exists
S1 records attempts, services, exact results, assessments and acceptance, and exports them as JSON.
What is owed
A coarse, versioned task descriptor. Projections that keep task counts apart from attempt counts and first-pass success apart from eventual success. Unassessed and excluded cases kept visible, and unknown costs never shown as zero. A station view that explains why each candidate pairing was considered or excluded. One Python instrument over the same JSON contracts.
A first piece
Issue #7: a Python instrument that reads an exported record and reports outcome counts by pairing and kind of task, every rate with its denominator, and no ranking. With it, a test design for routing: before the project claims routing helps, routed choices are compared against a baseline that keeps the same verified handoff.
Suits
Python, statistics on small samples, honest reporting.
2

Checks the builder never sees

Slice S3
Above the line
A published check is a target. We have found private checks in benchmarks and in one personal rig, and in no product a person can point at their own work.
What exists
The project's first paired run sealed its hidden checks outside every repository before the builders started, and its work order carried only their hash. That is procedure, and the product does not do it yet.
What is owed
An evaluation-pack interface. A code pack in which a new-behavior test fails on the base and passes on the candidate, while a regression guard passes on both. Receipts built by a trusted controller. Candidate code run as hostile code, with bounded inputs and limited feedback. A protected boundary, such as a separate Windows account or an encrypted store whose key never reaches an agent's process. A procedural mode stays available and is labelled weaker.
A first piece
Issue #8: the evaluation-pack interface and a code pack that runs a sealed check set against a candidate in a container. Harbor, an Apache-2.0 evaluation framework from the creators of Terminal-Bench, already runs agents and custom benchmarks in containers, and it is the first runner to evaluate before writing one.
Suits
TypeScript, process isolation on Windows and Linux, containers, test runners.
3

Acceptance for results that are not code

Slice S3
Above the line
Every acceptance tool we have read is built for code. People already combine services for images, narration, video and text, and they need the same rule for each part and for the whole.
What exists
S1 imports any file as exact bytes, runs simple deterministic checks (a non-empty file, a required text), and records the steward's judgment for the rest.
What is owed
A media and document pack (image dimensions and format, audio and video duration and codec, document structure) that reports pass, fail, unknown or error. Integration checks over a result's parts, so inputs that each pass can still produce a rejected whole. Safe previews in the station that never run a file as code.
A first piece
Issue #9, an assessment pack for images, together with issue #5, safe previews.
Suits
TypeScript, media formats, careful parsing of untrusted files.
4

The steward's judgment as evidence

Slices S1, S3 and S5
Above the line
Meaning and taste need a person. The tools we have read end in a review state or an approve button. OpenCorral records the judgment as attributed evidence on a criterion, bound to the exact bytes judged, so the record can count it.
What exists
Judgments are recorded as the steward's, on a criterion, for an exact result.
What is owed
Rubrics versioned with the objective's contract. A judgment that goes stale when the bytes or the rubric change. Changed preferences, changed rubrics and real defects kept as separate denominators, so a pairing is never charged for a later change in what was wanted.
A first piece
Issue #10: versioned rubric criteria, and the station view that shows a judgment beside the bytes it judged.
Suits
TypeScript, interface design, data modelling.
5

Relay and allotment

Slice S2
Above the line
Many services expose no programmatic seam, and subscriptions come in windows. Showing remaining quota is a crowded category. Tying each window to an objective's budget, and refusing to work around a vendor's limits, is the corral's job.
What exists
The manual relay: copy a work order to any service, then import what comes back.
What is owed
Shared resource accounts and subscription windows. Reservations against a shared allowance that never count usage twice. An objective budget that covers retries, reviews and replanning. A durable command outbox that recovers from a crash at every step. The first automated adapter, chosen by what each harness actually exposes. The corral never spreads one person's load across several accounts of one vendor and never handles a vendor's login token.
A first piece
Issue #6, the first automated adapter, or issue #11, the reservation model with its crash-recovery tests.
Suits
TypeScript, SQLite, recovery and idempotency.

Below the line, OpenCorral is designed to plug in. The acceptance gate is designed to ship as a plugin behind existing execution orchestrators, the private checks can run on an existing evaluation runner, and a model reviewer may advise a grade without ever passing a gate. The seams are in the architecture, section 9.

Neighbors.

Developers ask how OpenCorral differs from tools they already know. Each card describes a neighbor from its own pages and says where OpenCorral stands beside it.

Omnigent

An Apache-2.0 meta-harness from Databricks, in alpha, over Claude Code, Codex, Cursor, OpenCode and agents you write yourself, with policies that pause for your approval or cap spend. It sits in the same layer above the harnesses. OpenCorral works at that height on the accepted result, and is being built to keep a record of which pairing produced it.

GitHub Agent HQ

GitHub's platform for running Copilot, Claude and Codex agents, where a team can assign one issue to more than one agent to compare results. OpenCorral is being built to keep such comparisons as graded evidence on your own machine, including work done in tools outside GitHub.

MartinLoop

In its own words, the system around the coding job: it launches agent runs, enforces budgets and path limits, and requires fresh verifier evidence bound to the run before completion. OpenCorral leaves the run to the harness, holds the objective across services, and is being built to carry each outcome into a record.

Execution orchestrators

Agent Orchestrator, Sortie, Bernstein and others run many agents in parallel worktrees and pull requests. OpenCorral is designed to plug in above them, with its acceptance gate shipped as a plugin behind them.

How to join.

  1. Read the README, the charter, sections 8, 10 and 11 of the architecture (acceptance, the operating range, routing), and the slice of the implementation plan your lane belongs to.
  2. Open an issue that names your lane and the first piece you would take, or comment on an existing one.
  3. Build it the way the project grades agents. A test for new behavior is seen failing before your change and passing after it, guards are declared as guards, the gates pass locally and in continuous integration, and a person approves every merge.
  4. Sign every commit with git commit -s under the Developer Certificate of Origin. You keep your copyright and license the work under Apache-2.0.

What is offered

Credit in the commit history, a lane you own, and the work itself. No paid work or equity is on offer today; anything of that kind will be announced publicly and in writing before it exists.
